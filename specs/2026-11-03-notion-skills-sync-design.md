# Notion as the source of truth for agent-skills

2026-11-03. **Approved.**

## Intent

Two general-purpose skills — *adding batch features* (`batch-features`) and *working from an
issue* (`work-issue`) — should be editable by people who don't use git. So the Notion Skills
database becomes their source of truth, and `hbardet/agent-skills` becomes the published copy: a
plugin marketplace generated by a scheduled sync. The repo stays the install source for
`~/.agents/skills` — `install.sh` is retargeted at the synced layout, so day-to-day use of the
skills doesn't change.

The skills are published **exactly as they are today**: same bodies, same `shared/` imports,
same behaviour. This piece of work is about the *architecture* for handling skills — Notion as the
source, GitHub as the published copy, one `.env`, one install path — not about rewriting the
skills' content. Content changes get their own conversation.

## What that means for `shared/` (known gap, accepted for now)

Notion can only attach files *inside* a skill's directory, so a root-level `shared/` cannot be
published. Two consequences, both visible now rather than discovered later:

- `shared/` stays hand-maintained in this repo and is still symlinked into `~/.agents/skills/` by
  `install.sh`. Both skills keep their `../shared/` / `~/.agents/skills/shared/` wording and keep
  working locally and after install — nothing about day-to-day use changes.
- The **published plugin is therefore incomplete for third parties**: `plugins/<slug>/skills/
  {batch-features,work-issue}/SKILL.md` reference `../shared/`, which is not in the synced tree.
  Anyone consuming the marketplace rather than `install.sh` gets two skills that point at a
  missing directory. Documented in `README.md` as a known limitation.
- Closing it is a later, content-level decision (inline the paragraphs each skill needs, or add a
  third `shared` row once we're willing to restructure). Out of scope here, per the user's call.

## Goals

- Both skills (and only those two) live in a Notion Skills database; edits there reach GitHub
  within the hour (or on a manual run).
- One GitHub Action publishes `plugins/<slug>/…` and `.claude-plugin/marketplace.json` into
  `hbardet/agent-skills` `main`.
- `install.sh` keeps symlinking both skills into `~/.agents/skills`, now reading the synced tree.
- Each published `SKILL.md` is byte-identical to today's, minus the frontmatter the renderer
  regenerates from the DB properties.
- All credentials and settings are in one filled-in `.env`; a script copies them onto the sync
  repo as Actions secrets/variables.

## Non-goals

- Reverse sync (repo edits → Notion). The sample is one-way; hand edits to `plugins/` are lost.
- Using Notion as the issue tracker. The tracker rules stay GitLab/GitHub only (gh / glab).
- Publishing `shared/` as its own row, or a per-project variant of either skill.
- Rewriting, improving, or generalising the skills' content. They ship as-is.

## Anti-goals

- Two editable copies of any skill text (Notion + repo) drifting apart.
- Committing tokens. `.env` is gitignored; only `.env.example` is committed.
- A first sync that deletes `skills/` before the replacement is proven.

## Constraints (verified, not assumed)

- **The plugin is the only publish unit.** `/v1/ai/plugins` lists `{id, name, description,
  version_id}`; `/v1/ai/plugins/:id` returns a signed `.tar.gz` of the whole plugin in the Agent
  Plugins 1.0 layout (`plugin.json` + `skills/<name>/…`). There is no skill-level endpoint and no
  per-row publish flag — access to the Notion connection is the publish control.
- **Skills DB schema** (typed `database_type: skills`): `Skill name`, `Description`, `Files`,
  `Tags`, `Created by`. `Files` attachments land beside the rendered `SKILL.md`; a `.zip` is
  expanded in place, so nested folders are expressible.
- **Both skills must belong to one plugin**, or they'd be published as two separate
  directories.
- **The workflow runs in the sync-script repo, not the target repo.** Secrets and variables are
  set there. GitHub rejects variable names starting with `GITHUB_`, hence `SKILLS_GITHUB_REPO` /
  `SKILLS_GITHUB_BRANCH`, mapped back in `sync.yml`.
- **This machine:** `gh` is authenticated as `hbardet` (ADMIN on the target, token scopes include
  `repo`); `ntn` is not installed globally but `npx --yes ntn` works (0.23.26); the target repo is
  public, default branch `main`, Actions enabled.

## Approaches considered

1. **Fork the sample and run its sync against this repo (chosen).** The fork holds the workflow
   and the credentials; `hbardet/agent-skills` is its target. Upstream fixes arrive with
   `bun run update`.
2. Vendor the tool into this repo (`sync/` + workflow). One repo, but its `update` merges from an
   `upstream` remote assuming it *is* the whole repo — so we'd lose the update path and gain a
   permanent copy to maintain. Rejected.
3. Write a minimal sync ourselves (~150 lines). No copied code, but no marker-based skip, no App
   auth, no write-back guidance; we'd own every future API change. Rejected: the sample is
   maintained by the API's own vendor.

Trade-off accepted with (1): two repos (tool fork + target), and a bot commits to this repo's
`main`.

**Correction after reading the sample's code: its `setup` wizard cannot be pointed at
`hbardet/agent-skills`.** `setup/steps/resources.ts:75-76` always creates a *new, private* skills
repo via `gh repo create`, and `setup/skills-db.ts:348` creates a new "Skills" DB pre-populated
with two sample skills. `setup --ci` (`setup/non-interactive.ts:120,141`) also creates a DB with
samples and forces the branch `setup-e2e-test` (`:169`); it never deploys the workflow or the
App. So the wizard is not used. Instead:

- **GitHub auth = a fine-grained PAT** in `GITHUB_TOKEN` (Contents: read & write on
  `hbardet/agent-skills`, one year). The wizard's App-creation flow is the only thing we give up;
  an App can replace the PAT later without changing anything else (`GITHUB_APP_ID` +
  `GITHUB_APP_PRIVATE_KEY` are already read by `src/config.ts`).
- **The DB is created and seeded by us** with `ntn` (see below), not by setup.
- **The workflow is already in the fork** (`.github/workflows/sync.yml`); deploying means
  `gh secret set` / `gh variable set` from `.env` and dispatching a run.

## Parts of the how, as decided

### Repositories

| Repo | Role |
|---|---|
| `hbardet/agent-skills` | Marketplace target. Holds generated `plugins/`, `.claude-plugin/marketplace.json`, plus hand-maintained `install.sh`, `specs/`, `docs/`, `config/`, `.env.example`. Public, `main`. |
| `hbardet/my-skills` | Fork of `makenotion/notion-skills-github-sync`. Holds `sync.yml`, its secrets/variables, and the local `.env` used for manual runs. Created during implementation. |

### Notion

- One typed Skills DB named **Agent Skills**, created under a parent page the user picks, and
  **one connection** ("Skills Sync") added to that DB and nothing else. The sync publishes every
  plugin the token can read (`src/notion/plugins.ts` → `listAll`), so scoping is the only thing
  that keeps unrelated workspace skills out of this marketplace.
- **Seeding writes through the same connection token.** `ntn pages create`/`ntn api` authenticate with
  `NOTION_API_TOKEN` (a public-API integration token, not the keychain login — `npx --yes ntn pages
  create --help`, 0.23.26). So the "Skills Sync" connection is created with **Read + Insert +
  Update**; after seeding its capabilities can be trimmed back to Read in Notion. Extra attribute:
  the connection must be added to the DB *and* its parent page, otherwise seeding the first row
  fails with "object not found".
- **`ntn pages create --parent data-source:<id> < body.md` converts markdown to blocks**, and
  strips a leading frontmatter block, setting the page title from frontmatter `title`. Non-title
  properties are ignored there, so the seed script PATCHes `Description`/`Tags` afterwards with
  `ntn api -X PATCH v1/pages/<id> -d @props.json`.
- **The DB itself is created by hand in the Notion UI** (one-time): the typed `skills` database
  type is a product feature, not something the public API can create. Everything after that is
  scripted.
- **Frontmatter is rendered from the properties, not from the body.** The sample seeds bodies with
  no YAML and gets a `SKILL.md` with frontmatter back (`test/notion-archive.test.ts:40-42`), so
  `scripts/seed-notion.ts` strips the YAML block from today's files and puts the full `description`
  into the DB `Description` property. The description is the long trigger text and must survive
  intact.
- **Body fidelity is the main risk.** `setup/skills-db.ts:117-140` (`bodyToBlocks`) handles only
  headings, lists, and paragraphs — our skills contain fenced code, tables, and blockquotes.
  Seeding must preserve them (API blocks, or `ntn`'s markdown import if it round-trips), and the
  discovery sync must diff the rendered `SKILL.md` against today's file. Acceptable = no loss of
  meaning; the "bodies ship unchanged" non-goal is what this check protects.
- **Two rows, no `shared` row:**
  - `batch-features` — body = today's `SKILL.md`, frontmatter stripped;
  - `work-issue` — same. No content edits.
- No `Files` attachments: the render is plain markdown, so the first sync is easy to diff and review.
- Discovery step: the first `bun run sync --dry-run` with the user's token confirms that both rows
  land in **one** plugin slug, and the diff against today's files shows only the regenerated
  frontmatter differing.

### Configuration: `.env.example`

Committed at **this** repo's root; `.env` itself is gitignored here. This repo holds the single
canonical copy. Local sync runs export it into the fork's process (`scripts/notion-sync.sh local`)
rather than duplicating the file; the workflow never reads `.env` at all, it reads the repo
variables/secrets set from it. No secret is ever written into the fork's git tree.

```dotenv
# --- Notion (source of truth) -------------------------------------------------
# Connection token with read access to the Agent Skills database. REQUIRED.
# Get it: notion.so -> Settings -> Connections -> New connection -> name it
# "Skills Sync" -> authentication method "Access token" -> pick your workspace ->
# Create -> copy the ntn_... token. Then open the Agent Skills DB ->
# "..." menu -> Connections -> Add connection -> "Skills Sync".
NOTION_API_TOKEN=ntn_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# prod (default) | dev | stg — flips the API host and the page links in plugin markers.
NOTION_ENV=prod

# Data source ID of the Agent Skills DB (from its URL / `ntn datasources resolve`).
# Optional: only recorded in each plugin's .notion-sync.json as a back-reference.
SKILLS_DATA_SOURCE_ID=

# --- Where the plugins are published -----------------------------------------
GITHUB_REPO=hbardet/agent-skills
GITHUB_BRANCH=main

# --- GitHub push credential: pick ONE block ----------------------------------
# (a) Fine-grained PAT — simplest. Contents: Read and write, only this repo.
# https://github.com/settings/personal-access-tokens/new
#   name "Notion Skills Sync", only select repositories -> hbardet/agent-skills,
#   Contents: Read and write. Copy the ghp_.../github_pat_... value.
GITHUB_TOKEN=

# (b) GitHub App — what the sample's setup creates by default (not tied to a
#     person, no expiry). The wizard fills these in for you; otherwise create an
#     App, grant Contents: read & write, install it on hbardet/agent-skills, and
#     download a private key. The key goes on ONE line with literal \n escapes.
GITHUB_APP_ID=
GITHUB_APP_PRIVATE_KEY=
# Optional; looked up from GITHUB_REPO when empty.
GITHUB_APP_INSTALLATION_ID=

# --- Commit identity (optional) ----------------------------------------------
GIT_AUTHOR_NAME=my-skills
GIT_AUTHOR_EMAIL=my-skills@users.noreply.github.com
```

Where each value ends up:

| `.env` name | Fork secret | Fork variable |
|---|---|---|
| `NOTION_API_TOKEN` | `NOTION_API_TOKEN` | — |
| `GITHUB_TOKEN` | `GH_PUSH_TOKEN` | — |
| `GITHUB_APP_ID` | — | `SKILLS_GITHUB_APP_ID` |
| `GITHUB_APP_PRIVATE_KEY` | `SKILLS_GITHUB_APP_PRIVATE_KEY` | — |
| `GITHUB_REPO` | — | `SKILLS_GITHUB_REPO` |
| `GITHUB_BRANCH` | — | `SKILLS_GITHUB_BRANCH` |
| `NOTION_ENV` | — | `NOTION_ENV` |
| `SKILLS_DATA_SOURCE_ID` | — | `SKILLS_DATA_SOURCE_ID` |
| `GIT_AUTHOR_NAME` / `_EMAIL` | — | same names |

`scripts/set-sync-config.sh <owner/sync-repo>` reads `.env`, pushes the rows above with
`gh secret set` / `gh variable set`, and sets nothing else. Tokens go through stdin, never argv.

### Repo changes in this repo

- `.env.example` (above) and `.env` in `.gitignore`.
- `docs/notion-sync-setup.md` — the same how-to-get-each-value text, plus the order of operations
  and the two admin settings that silently block Notion connections
  (`setup/guidance.ts`: "Limit who can create personal access tokens" and "Limit who can create
  internal connections").
- `scripts/set-sync-config.sh` — `.env` → fork secrets/variables.
- `scripts/notion-sync.sh {local|dry-run}` — runs the fork's `bun run src/cli.ts sync` with `.env`
  exported, so manual syncs never need a second copy of the file.
- `scripts/seed-notion.ts` — one-off: reads `skills/*/SKILL.md` unmodified (only the YAML block is
  split off into the DB properties), creates the two rows (body, description, tags) in the Agent
  Skills DB via `ntn`. Used once to move content into Notion; afterwards Notion is authoritative.
- `install.sh` — symlink `plugins/<slug>/skills/{batch-features,work-issue}` **plus the repo's
  `shared/`** into `~/.agents/skills`. While `skills/` still exists it is the fallback; once the
  synced tree is verified, the fallback is deleted so there is exactly one source per skill.
- `README.md` + `AGENTS.md` — Notion is the source of truth; `plugins/` is generated, never
  hand-edited; `shared/` is still git-maintained; how to add a skill (new Notion row, wait for the
  sync); the "plugin lacks `shared/`" limitation above.
- **Deleted after the first verified sync:** `skills/` only. `shared/` and `config/` stay
  hand-maintained in the repo (see the `shared/` section above).

### Order of operations

1. Land `.env.example`, `.gitignore`, docs, scripts, and the `install.sh` fallback (no behaviour
   change yet). The user fills `.env`.
2. Fork the sample to `hbardet/my-skills` (private), `bun install`, and `ntn login`.
3. Create the Agent Skills DB under the Notion page **Process IA**
   (`https://app.notion.com/p/Process-IA-40d901c190a1808cb01ff0115d8c9e2a`); create the
   "Skills Sync" connection, add it to that DB only, and put its token in `.env`.
4. Seed the two rows with `ntn` (frontmatter stripped, descriptions intact, bodies untouched).
5. `scripts/notion-sync.sh dry-run` → diff rendered `SKILL.md` vs today's files; fix seeding
   fidelity; confirm both rows land in one plugin slug.
6. `scripts/set-sync-config.sh`; real sync; verify `install.sh` against `plugins/…` in a fresh
   shell; delete `skills/`; update README/AGENTS.md.
7. Dispatch the workflow once from the fork; confirm the hourly schedule is registered and a
   second run is a no-op (the idempotency proof the sample's own verify step makes).
