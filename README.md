# agent-skills

Portable skills for the two ends of a superpowers-based dev workflow:

- **`batch-features`** — turn a pasted list of rough ideas into well-formed tracker issues,
  with a per-item debate before anything is filed.
- **`work-issue`** — take an issue from `ready` to a merge request, delegating to
  `obra/superpowers` for planning, execution, review, and branch finishing.

Neither skill modifies superpowers. Both invoke them.

## Where the skills live

**Notion is the source of truth.** Both skills are rows in the *Skills* database on the
[Process IA](https://app.notion.com/p/Process-IA-40d901c190a1808cb01ff0115d8c9e2a) page
(data source `40d901c1-90a1-80ed-ad69-000b4515f34b`). Edit the row, not this repo.

[`hbardet/my-skills`](https://github.com/hbardet/my-skills) polls that database hourly and commits
the result here: `plugins/agent-skill/skills/<name>/SKILL.md` plus the marketplace manifests. **Never
hand-edit `plugins/`** — the next sync overwrites it, and a local edit is lost without a diff anyone
can review.

Two things are still maintained by hand in git:

- `shared/` — the tracker adapter, issue template, labels, and config schema the skills read.
- `config/` — the starter `.agent-skills/config.json`.

Known limitation: a consumer that installs straight from the marketplace gets `plugins/<slug>/skills/…`
with no `../shared/` next to it, so `shared/…` reads fail. `install.sh` links this repo's `shared/`
for exactly that reason — install from a clone, not from the marketplace.

## Install

```bash
git clone https://github.com/hbardet/agent-skills.git
cd agent-skills
./install.sh          # symlinks the synced skills into ~/.agents/skills
```

`install.sh` links each skill from `plugins/*/skills/` (falling back to `skills/` in a pre-sync
checkout) and always links `shared/`.

`install.sh` is idempotent and safe to re-run on any machine. Set `AGENTS_SKILLS_DIR` to override
the target directory.

## Layout

```
plugins/agent-skill/skills/     generated by the Notion sync — do not edit
.claude-plugin/ .cursor-plugin/ .agents/plugins/
                                marketplace manifests, generated too
shared/                         tracker adapter, issue template, labels, config schema
config/                         per-repo config templates (optional)
specs/                          design docs for the skills themselves
docs/notion-sync-setup.md       how the Notion → repo pipeline is wired
scripts/                        the local half of that pipeline (seed, sync, config)
test/fixtures/skills/           frozen originals, the source a reseed reads
install.sh                      symlink installer
```

| Skill | What it does |
|---|---|
| `batch-features` | intake: list → debate → review table → issues |
| `work-issue` | pickup: issue → worktree → plan → execute → MR |

## Where the spec and plan live

Neither lives in the project repo. The **spec is the tracker issue body** (read from the
issue), the **plan is a comment on the issue** (web-editable), plus a disposable local copy under
`~/.agent-skills/state/<owner>/<repo>/plans/` because superpowers' scripts take a file path.
The repo gets code and the MR.

## Tracker support

GitLab (`glab`) and GitHub (`gh`). Detected from `git remote -v`; the per-repo
`.agent-skills/config.json` stores the choice and the conventions.
